MJWarp Derivative Validation

Can GPU-batched finite differences replace CPU MuJoCo transition Jacobians for contact-rich trajectory optimization? Unitree Go1, 7 state categories, 9 epsilons, 3 simulators.

Verdict: yes for smooth and stable-contact states, with a usable epsilon window ~100× wider than CPU double precision — but the GPU is not faster than 32 CPU threads on a robot this size.

Where the MJWarp Jacobian is inaccurate, the CPU float64 Jacobian is inaccurate in exactly the same way: near contact switching, both fail identically. That failure is contact nonsmoothness, not float32. A float64 GPU control (MJX) isolates the remaining gap as pure precision.

1 · The CPU implementation is exact

Before comparing anything on a GPU, the manifold-aware black-box central difference has to reproduce MuJoCo's own mjd_transitionFD. Across 7 fixtures × 5 epsilons it agrees to 1.47e-16 relative Frobenius — machine precision. Tangent perturbation via mj_integratePos, output differencing via mj_differentiatePos, state packing, control indexing and warm-start handling are therefore all correct, and every later discrepancy belongs to the simulator rather than to the harness.

Gotcha worth recording: a diagnostic mj_forward placed inside the FD loop shifts the Jacobian by ~1e−6 even if qacc_warmstart is saved and restored around it. Contact diagnostics must run on a separate MjData.

3 · Precision, isolated

Three simulators, identical model and options (pyramidal cone, the one MJX supports), identical perturbations, same GPU. The y axis is the relative error of A against a CPU float64 reference at h=1e−6.

CPU float64MJWarp float32 (GPU)MJX float64 (GPU)
  • CPU float64 falls as O(h²) and keeps falling — it never reaches a roundoff floor in this range.
  • MJX float64 on the GPU tracks the CPU curve almost exactly. GPU batching by itself costs nothing: agreement with CPU is ~1e−12 for flight, sliding and impact.
  • MJWarp float32 turns around near h≈1e−3…1e−4 and climbs again. That U is the whole story: truncation on the right, float32 cancellation and nondeterminism on the left.
  • For onset, all three curves are identical at large h — including the two float64 ones. That error is not precision.
  • loaded has no MJWarp curve at all: it returns NaN at every epsilon under this configuration. See below.

A float32 failure that only appears in a batch

With the pyramidal cone, the loaded fixture — 8 contacts, 3 cm penetration, 68 active constraints — makes MJWarp return NaN in 10 of the 97 perturbed worlds, which poisons 8 columns of A and therefore the entire Jacobian. The nominal unperturbed step is fine, and CPU float64 and MJX float64 handle the identical states without trouble (max|qvel| = 0.664 for all of them).

The sharp part: re-running those same 10 states one world at a time, 9 of the 10 come back finite. Re-running them as a 10-world batch, they NaN again. Whether the solve diverges depends on the batch it is evaluated in — so this class of failure will not reproduce in a single-world debug session, and it is invisible unless every returned world is checked for finiteness. The elliptic-cone configuration of the same fixture does not exhibit it.

Practical consequence: validate isfinite on every perturbed world before assembling A and B, and treat a NaN world as a failed column rather than letting it propagate.

MJWarp is bitwise reproducible when there are no contacts (flight: exactly zero across 5 runs) and nondeterministic as soon as the constraint solver is active, with the spread growing like η/h as h shrinks — precisely the mechanism the plan predicted. MJX float64 shows the same structure five to eight orders of magnitude lower.

5 · Splitting contact-stable from contact-changing columns

The plan warns that mixing both into one Frobenius norm hides the behaviour. It does.

contact-stable columnscontact-changing columns

At onset, h=1e−4: the 32 contact-stable columns carry a relative error of 4.3e−2 while the 4 contact-changing columns carry 3.1e+1 — nearly three orders of magnitude apart, averaged into a single misleading number if reported together. Column count that stays contact-stable rises from 22/36 at h=1e−2 to 36/36 at h=1e−5.

CUDA graph capture is not optional. Launched eagerly, one batched step of 97 worlds costs 25 ms of Python kernel-launch overhead; captured into a graph it costs 0.37 ms — a 20–55× difference that has nothing to do with physics. Any benchmark run without it is measuring the wrong thing.

Even so, 96 worlds is far too small a batch to saturate a 4090. A single Jacobian for a 12-DoF quadruped is cheaper on 32 CPU threads than on the GPU at every horizon tested.

Batching many shooting knots at once is the scenario that should favour the GPU. It does help — cost per Jacobian falls from 1.49 ms at K=1 to 0.91 ms at K=4 — but it never reaches the 0.47 ms the CPU pool sustains, and past K=4 it gets worse again (1.84 ms at K=12) as memory pressure grows. The CPU curve, by contrast, is flat to slightly improving out to K=64.

MJWarp also hits a memory wall well before the SMs are busy. Data allocation grew roughly quadratically in world count for this model (405 MB at 192 worlds → 1.5 GB at 384 → 6.1 GB at 768), and the default nccdmax — convex-collision scratch that the Go1 does not need, having only primitive collision geometry — accounted for much of the captured-graph footprint (10.6 GB → 2.7 GB at 384 worlds once capped). Passing nccdmax and a realistic njmax explicitly to put_data is the difference between fitting 8 knots and fitting 2 on a 24 GB card.

8 · What to do with this

  • Use h ≈ 1e−3 for MJWarp, not the CPU value. Carrying the double-precision epsilon over costs two to three orders of magnitude of accuracy.
  • Always capture the step into a CUDA graph and size njmax to the real per-world nefc (48 here, not 512).
  • Log contact-set equality per perturbation and report contact-stable and contact-changing columns separately; a single Frobenius norm is uninformative near switching.
  • Do not expect the GPU to pay off for one robot-sized Jacobian. The competitor is mujoco.rollout with a persistent thread pool, not single-threaded mjd_transitionFD, and it wins here.
  • Near-switching states need a different tool — randomized smoothing, contact-implicit formulations or bundled gradients — because the CPU float64 Jacobian is equally non-predictive there.
